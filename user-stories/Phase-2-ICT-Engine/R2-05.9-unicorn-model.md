## Objective

Implement the Unicorn as a **composite of a Breaker Block and an FVG**, never as a
standalone pattern. `UnicornDetector` consumes both upstream detectors and detects
nothing itself beyond geometry.

## Dependencies

```
Breaker Block (R2-05.4) ┐
                        ├─► same polarity + price overlap ─► Unicorn
FVG (R2-05)             ┘
```

## Exact semantics

**Inputs.** One confirmed Breaker Block and one confirmed FVG, same symbol and
timeframe.

**Polarity must match.** Per the source: *"A bullish Breaker Block overlapping a
bullish Fair Value Gap"* and the bearish mirror. Opposite-polarity overlaps are not
Unicorns (that pairing is a BPR-shaped idea, and is not this).

**Partial overlap is sufficient** — full containment is **not** required. The source
describes marking every Breaker *"then check whether any of those Breaker Blocks have a
Fair Value Gap overlapping them."*

**Zone = the intersection**, per *"the shaded overlap area between the Breaker Block and
the Fair Value Gap is the Unicorn entry zone"*:

```
zone_top    = min(breaker.zone_top,    fvg.top)
zone_bottom = max(breaker.zone_bottom, fvg.bottom)
```

**Strictly positive overlap required.** Touching at a single price is not an overlap;
a zero-width Unicorn is refused at construction, never stored.

**Adjacency.** The FVG must confirm within `max_bars_from_breaker` bars of the Breaker
(finite documented default), reflecting the source's *"fresh, in-context overlap"* and
its association with the same structural leg. Unbounded pairing would match a Breaker
against an unrelated gap much later.

**Cardinality — no collapsing.** One Unicorn per qualifying **(breaker, FVG) pair**.
Three FVGs overlapping one Breaker produce **three** Unicorns with three ids; two
Breakers overlapping one FVG produce **two**. No deduplication, no "best" selection, no
merging of overlapping zones. This is an explicit requirement, not an optimisation
opportunity.

**Retest is not confirmation.** The source describes a retest confirming the Unicorn as
a *trade*; the *event* exists as soon as both components are confirmed and overlap.
Retest is recorded in the update stream. Conflating the two would defer the event to an
arbitrary later instant and make it unobservable in replay.

**Lifecycle.** `ACTIVE` → `PARTIALLY_FILLED` → `MITIGATED` against the Unicorn's own
zone. Additionally the Unicorn is `INVALIDATED` when its **source Breaker** is
invalidated — a Unicorn cannot outlive the Breaker that defines it. The invalidation is
inherited by reference, never recomputed.

## Event schema

```
Unicorn (frozen)
    unicorn_id              "unicorn:<symbol>:<timeframe>:<confirmation ts ISO>:<pair hash>"
    breaker_block_id        provenance — resolves in the same analysis
    fvg_id                  provenance — resolves in the same analysis
    symbol, timeframe, direction
    zone_top, zone_bottom, overlap_points
    event_timestamp         the later component's event timestamp
    confirmation_timestamp  max(breaker.confirmation, fvg.confirmation)
    status                  UnicornStatus

UnicornUpdate (frozen)      retest / fill / inherited invalidation, timestamped
```

Contract additions: `EventType.UNICORN_BULLISH`, `EventType.UNICORN_BEARISH`.

## Timestamp semantics

| | |
|---|---|
| `event_timestamp` | the later of the two components' event timestamps |
| `confirmation_timestamp` | `max(breaker.confirmation, fvg.confirmation)` |
| invariant | `>=` both components' confirmations; a Unicorn observable before either component is a contradiction |

## Leakage acceptance criteria

Inherits L1–L6. Story-specific:

- **L4 (mandatory):** the naive implementation stamping the Unicorn at the **FVG's**
  confirmation when the Breaker confirms later is implemented and proven to publish
  Unicorns before their Breaker exists.
- No Unicorn is observable before **both** components are observable.
- Both provenance ids resolve within the same analysis.
- Opposite-polarity overlaps produce nothing (adversarial).
- Touching-but-not-overlapping zones produce nothing (adversarial).
- Multiple qualifying pairs produce multiple distinct ids — asserted explicitly, since
  silent collapsing is the failure mode this story is most likely to hit.

## Real-data acceptance criteria

EURUSD + XAUUSD on 1m / 5m / 15m / 1H / 4H. Report Unicorn counts per timeframe, the
observed cardinality distribution (how many FVGs per Breaker), and three real examples
with both provenance ids, overlap width and all timestamps.

**A genuine zero is an expected and acceptable result.** The source calls the overlap
rare; on a four-day fixture, zero Unicorns on some or all timeframes is a valid
finding and must be reported as such rather than engineered away by loosening
thresholds.

## Batch / streaming criteria

`batch == prefix replay == bar-by-bar`, including the update stream and inherited
invalidation.

## Known limitations (anticipated)

1. Inherits every limitation of the OB qualifier and the Breaker reading beneath it.
2. `max_bars_from_breaker` is a configured proxy for the source's informal
   "same structural leg".
3. Pairwise enumeration is O(breakers × FVGs) within the window.
4. The four-day fixture may contain too few Breakers for a meaningful count.

## Out of scope

Entries, retest-based signals, scoring, ML, Kronos, cross-timeframe projection.
