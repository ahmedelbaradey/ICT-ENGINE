# R2-05.2 — Inversion Fair Value Gap (IFVG)

- **Project:** ICT-Kronos · **Phase:** Phase 2 — ICT Engine · **Issue type:** Story
- **Story points:** 3 · **Labels:** `ict`, `ifvg`, `composite`, `leakage`
- **Depends on:** R2-05 (FVG) · **Blocks:** R2-05.9 (Unicorn context)
- **Concept map:** [R2-05x-CONCEPT-MAP.md](../../docs/ict/R2-05x-CONCEPT-MAP.md) §5.2

## Objective

Implement the Inversion Fair Value Gap as a **state transition of an existing FVG**,
not as a new pattern. `IfvgDetector` consumes `FvgDetector` output; it does not
re-detect gaps.

This story also builds the shared composite machinery (`assert_provenance_resolves`,
`assert_sources_observable_first`) that R2-05.3 … R2-05.9 reuse.

## Dependencies

```
FVG (R2-05) ──► price closes through the zone against its polarity ──► IFVG
```

Consumed, never reimplemented: `FvgDetector`, `FvgZone`, `FvgAnalysis`.

## Exact semantics

**Inversion trigger (proposed default — `CLOSE_THROUGH_FAR_EDGE`).** A bullish FVG
inverts when a bar **closes below** the zone's `far_edge` (its bottom). A bearish FVG
inverts when a bar **closes above** its `far_edge` (its top). Mirror-symmetric.

The trigger reads a **close**, per the source: *"An IFVG forms when price closes beyond
a Fair Value Gap."* A wick through the zone is explicitly **not** an inversion.

Configurable alternatives, documented and not default: `CLOSE_INSIDE_ZONE` (a close
anywhere beyond the near edge) and `WICK_THROUGH` (present only so the naive
implementation can be exercised in tests — never a recommended setting).

**Mitigation is not inversion.** R2-05 computes fill from bar *extremes*, so a wick can
mitigate a gap 100% without any bar closing through it. Such a zone is `MITIGATED` and
is **not** an IFVG. The two are different questions about the same zone and both remain
answerable. This is the single most important sentence in the story.

**Polarity flips.** A bullish FVG produces a **bearish** IFVG and vice versa. The zone
geometry (`top`, `bottom`) is inherited unchanged from the source FVG.

**One inversion per FVG, terminal.** An FVG inverts at most once. The resulting IFVG
has its own independent lifecycle; it does not invert back into an FVG.

**IFVG lifecycle.** `ACTIVE` → `PARTIALLY_FILLED` → `MITIGATED`, computed against the
inverted polarity by the same fill arithmetic R2-05 uses, from the inverting bar
onward. `INVALIDATED` is a synonym for full mitigation, as in R2-05.

## Event schema

```
IfvgZone (frozen)
    ifvg_id                 "ifvg:<symbol>:<timeframe>:<inversion ts ISO>"
    source_fvg_id           provenance — resolves to an FvgZone in the same analysis
    symbol, timeframe
    original_direction      the source FVG's polarity
    direction               the inverted polarity (what the IFVG now is)
    zone_top, zone_bottom   inherited from the source FVG, unchanged
    event_timestamp         the inverting bar's OPEN
    confirmation_timestamp  the inverting bar's close_time
    source_fvg_confirmation the source FVG's confirmation (for the §L6 invariant)
    close_through_price     the close that triggered inversion
    status                  IfvgStatus

IfvgFillUpdate (frozen)     zone_id, event_timestamp, confirmation_timestamp,
                            fill_percentage, deepest_price, status_after
```

Contract additions: `EventType.IFVG_BULLISH`, `EventType.IFVG_BEARISH`.

## Timestamp semantics

| | |
|---|---|
| `event_timestamp` | the inverting bar's open — where the flip sits on the chart |
| `confirmation_timestamp` | the inverting bar's **close_time** — the trigger reads a close |
| invariant | `confirmation_timestamp` > `source_fvg.confirmation_timestamp`, strictly: the inverting bar is necessarily later than C3 |

Confirmation lag is exactly one bar duration, always — the same shape as R2-05.

## Leakage acceptance criteria

Inherits L1–L6 ([concept map §4](../../docs/ict/R2-05x-CONCEPT-MAP.md#4-leakage-criteria--the-shared-pattern)). Story-specific:

- **L4 naive divergence (mandatory):** implement the wick-based inverter and prove it
  reports inversions the causal implementation does not, and reports them earlier.
- No IFVG is observable before its inverting bar closes.
- Mutating bars after the inverting bar cannot change the IFVG; mutating that bar's
  **close** does (the control).
- A source FVG that is only wick-mitigated produces **no** IFVG.
- `filter_observable` on IFVGs never returns one whose source FVG is not yet observable.

## Real-data acceptance criteria

EURUSD + XAUUSD on 1m / 5m / 15m / 1H / 4H. Report inversion counts per timeframe and
at least three real inversion examples with source FVG id, both timestamps, and the
triggering close. A genuine zero on a sparse timeframe is a valid result (R2-05
precedent) and must not be forced.

## Batch / streaming criteria

`batch == prefix replay == bar-by-bar`, including the fill stream. Appending bars may
add IFVGs and fill updates but must never alter an existing record.

## Known limitations (anticipated)

1. Inversion is timeframe-local; no cross-timeframe projection (R2-07).
2. `CLOSE_THROUGH_FAR_EDGE` makes IFVG strictly rarer than mitigation — a deliberate
   conservative choice that will under-count relative to looser published readings.
3. Fill scanning is O(bars × active zones), as in R2-05.

## Out of scope

BPR, Breaker, Unicorn, ML, Kronos, cross-timeframe projection, signals.
